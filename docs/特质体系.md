# 分部帽特质体系（Trait System）

> 本文是《题库与体验重构方案.md》§二十「尚未确定内容」的定稿结果。
> 出题、评分、雷达图、结果页文案一律以本文为依据。
> 信息源优先级仍遵循 `docs/README.md`：代码 > 本文 > 导出产物。

---

## 1. 为什么要独立一套 Trait

现有评分只有四部门分数（`p` +3 / `s` +1），雷达图的四根轴就是四个部门，
用户一眼就能看出测试机制。重构方案 §五、§六 要求把雷达图换成人格特质，
并且**禁止**「一个特质 = 一个部门」的换名式做法。

因此本轮采用**双轨并行**：

```
选项
 ├─ p / s ──→ 部门分数 ──→ 部门推荐（保持现状，不动）
 └─ traits ─→ 特质分数 ──→ 人格画像（新增）
```

两条链路互不依赖，都是纯函数、零随机。

### 为什么保留 p / s

`p` / `s` 的「4 个 p 覆盖四部门 + 4 个 s 构成无固定点置换」这条约束，
是当前保证「四个选项吸引力接近、四个部门都可达」的唯一机制，
`scoring.test.ts` 的穷举验证与 `simulate.test.ts` 的均衡断言都建立在它之上。
若改成由 Trait 反推部门，这套保障会连同全部测试基线一起失效。
保留 p/s 的代价只是每个选项多填一个 `traits` 字段。

## 2. 五个特质

| ID | 中文名 | 一句定义 |
| --- | --- | --- |
| `explore` | 探索 | 面对未知时倾向于主动接近、先走一步。 |
| `insight` | 洞察 | 倾向于观察细节、追问事情背后的原因。 |
| `create` | 创造 | 倾向于把想法变成具体存在的东西。 |
| `guard` | 守护 | 重视稳定、持续，让事情能可靠地运转下去。 |
| `connect` | 连接 | 倾向于通过人与人、信息与资源的联系推动事情。 |

规范顺序（雷达轴序、分数表键序）：

```
explore → insight → create → guard → connect
```

### 2.1 容易写歪的地方

| 特质 | 是 | 不是 |
| --- | --- | --- |
| 探索 | 先迈出那一步 | 鲁莽、不做准备 |
| 洞察 | 想弄清规则本身 | 聪明、智商高 |
| 创造 | 动手做出东西 | 有创意、有天赋 |
| 守护 | 让它继续能用 | 保守、不愿改变 |
| 连接 | 把人和资源接上 | 外向、会social |

**红线**：特质名与特质描述都不得写成能力评定或心理诊断
（`docs/注意事项.md` 规定结果不用于心理诊断/能力评定/录取筛选）。
文案只描述「你倾向于怎么做」，不写「你擅长/不擅长」。

## 3. 特质与部门的关系

刻意做成**多对多**。每个部门由 1 个主构成 + 2 个次构成特质组成：

| 部门 | 主构成 | 次构成 |
| --- | --- | --- |
| `dev` 开发部 | 创造 | 探索、连接 |
| `sec` 网络安全部 | 洞察 | 探索、守护 |
| `ops` 运维部 | 守护 | 洞察、连接 |
| `pr` 组宣部 | 连接 | 创造、探索 |

反向看，每个特质都被至少两个部门共用：

| 特质 | 出现在 |
| --- | --- |
| 探索 | dev 次、sec 次、pr 次 |
| 洞察 | sec 主、ops 次 |
| 创造 | dev 主、pr 次 |
| 守护 | sec 次、ops 主 |
| 连接 | dev 次、ops 次、pr 主 |

**这张表只用于出题时校准与结果页文案措辞，不参与任何计算。**
部门推荐永远来自 `p`/`s`，画像永远来自 `traits`。
两者可以相关，但不允许互相推导 —— 这正是 §六 的要求。

## 4. 计分规则

### 4.1 选项权重预算

每个选项的 trait 权重之和**恒等于 3**（`OPTION_TRAIT_BUDGET`）。
单个权重取 1～3 的整数，权重为 0 的特质**不写这个键**。

因此每个选项只有三种形态：

```
3        单一倾向鲜明
2 + 1    主次分明（推荐主力形态）
1 + 1 + 1  中间型
```

固定预算的用处：四个选项对画像的「总影响力」一样大，
用户不会因为选了写得更饱满的选项而拿到更高的总分。

### 4.2 归一化

分母不是固定常数，而是**全库理论上限**：

```
理论上限[t] = Σ(每题 4 个选项中 t 的最大权重)
归一化[t]   = 实得[t] / 理论上限[t]
```

不用固定常数是因为出题时权重一改，固定分母下的百分比就会整体漂移。
理论上限随题库自动重算，出题人不需要回头调常数。

`理论上限[t] === 0` 时归一化取 0（防除零，与 `scoring.ts` 的 `normalize` 同口径）。

### 4.3 画像排序与并列

- 画像按归一化分数降序取首位作为「主导特质」。
- 并列时按 §2 的规范顺序取首个，**并在文案上承认并列**（例：「两种倾向在你身上分得很近」）。
- 特质并列**不影响**部门推荐，也不影响 `explain.ts` 已有的 `runnerUp`。

### 4.4 「次要倾向」归属

重构方案 §八 的「它还在考虑：XX 部」沿用 `explain.ts` 已有的 `runnerUp`（部门亚军），
**不是**第二特质。理由：`runnerUp` 已有实现与测试覆盖，且「还在考虑另一个部门」
在语义上必须是部门，不能是特质。

## 5. 槽位矩阵（12 槽 × 2 候选 = 24 题）

题库不是一张固定的 12 题清单，而是 12 个**槽位**（`QuestionSlot`），
每槽放 2 道同类型、同对比轴的候选题。每次答题时按种子从每槽抽 1 道，
凑成一场 12 题的 `QuestionBank`。这样抽出的任何一组都自动满足下面的全部硬约束。

| 槽 | `kind` | 观察什么 | 备注 |
| --- | --- | --- | --- |
| q1 | `scenario` | 探索 ↔ 洞察 | 遇到问题第一反应 |
| q2 | `fantasy` | 探索 ↔ 守护 | 世界观建立题 |
| q3 | `scenario` | 创造 ↔ 连接 | 手上有个想法 |
| q4 | `resource` | 创造 ↔ 探索 | 一天自由时间 |
| q5 | `scenario` | 洞察 ↔ 守护 | 发现异常 |
| q6 | `priority` | 守护 ↔ 连接 | 四件事同时发生 |
| q7 | `fantasy` | 洞察 ↔ 连接 | 无署名的线索 |
| q8 | `scenario` | 连接 ↔ 创造 | 一群人卡住了 |
| q9 | `resource` | 守护 ↔ 探索 | 只能带走一件东西 |
| q10 | `abstract` | 洞察 ↔ 创造 | 关于「想明白」这件事 |
| q11 | `fantasy` | 探索 ↔ 连接 | 四条路 |
| q12 | `decider` | 五特质全覆盖 | `decider: true`，价值观题 |

题型配比（对应 §十）：情境 4 / 奇幻 3 / 资源 2 / 抽象 1 / 决胜 1，
其中技术味场景不超过 2 题。**两道候选题共用槽位的 `kind` 与 `axis`，
所以补候选不会打破配比。**

「观察什么」是这道题的**主要对比轴**，不代表该题只能出现这两个特质。
槽位号刻意不连续排布也无所谓 —— `q12` 永远是唯一的决胜槽且排在最后。

候选题 `id` 用「槽位号-序号」（`q1-1`、`q1-2`），它是答案表的键，必须全池唯一。

## 6. 出题顺序

必须按此顺序，不得先写选项再倒推权重（§二十一）：

```
① 确定这题想观察什么 → 查 §5 矩阵
② 写 scene
③ 写 4 个选项正文（先不管权重）
④ 给 4 个选项分配 traits（预算恒为 3）
⑤ 再分配 p / s（4 个 p 覆盖四部门，4 个 s 无固定点置换）
⑥ 写 whisper
⑦ 写 detail
⑧ 跑 npm run test 与 npm run simulate
```

④ 与 ⑤ 是两次独立分配。**不要让 traits 主导特质与 p 部门形成固定对应**，
否则等于又把部门写回了答案里。

## 7. 硬约束一览

由 `src/lib/validateBank.ts` 强制，违反即测试失败：

| 规则 | 内容 |
| --- | --- |
| `trait-weight-sum` | 每个选项 trait 权重之和 = 3 |
| `trait-weight-range` | 每个权重为 1～3 的整数 |
| `trait-question-spread` | 每题 4 个选项合计覆盖 ≥ 4 个不同特质 |
| `trait-bank-coverage` | 每个特质至少在半数题目中出现 |
| `option-text-length` | 见下表 |
| `forbidden-terms` | 题面/选项/低语/点评均不得出现部门名、拉丁名、部门关键词 |
| `privacy-terms` | 不得出现学号、手机号、QQ/微信号、邮箱、内网地址等模式 |

槽位与抽题层另有一组规则，由 `validateQuestionPool` 强制：

| 规则 | 内容 |
| --- | --- |
| `unique-slot-id` | 槽位号全池唯一 |
| `slot-not-empty` | 每槽至少 1 道候选 |
| `slot-candidate-count` | 各槽候选数必须一致（当前目标 2） |
| `slot-decider-consistent` | 决胜槽的候选必须 `decider: true`，其余槽必须不是 |
| `slot-axis-consistent` | 候选题必须真的落在槽位声明的对比轴上 |
| `single-decider-slot` | 恰好一个决胜槽 |
| `subset-*` | **穷举全部抽法**（≤4096 组合），逐组再跑一次 `unique-question-id` / `single-decider` / `trait-bank-coverage` |

`subset-*` 是题池化后最重要的一层：它保证「碰巧抽到一组失衡的题」不可能上线 ——
这种偶发失败必须在测试里就被摁死，而不是等用户抽到。

字数区间（沿用 `docs/题目填写规范.md`，本轮从注释升级为可执行校验）：

| 字段 | 区间 |
| --- | --- |
| `title` | 4～10 |
| `scene` | 30～60 |
| `text` | 12～28 |
| `whisper` | 15～30 |
| `detail` | 35～60 |

`whisper` 需带 `「」`，计数时不含引号。

## 8. 版本与分享码

本轮题库为**语义级 + 结构级**改动（`docs/题目填写规范.md` 的 B 类，且数据结构本身换了形状），因此：

- `QUESTION_POOL.version`: 1 → 3（v2 是过渡期的固定 12 题，未对外发布）
- `CAMPAIGN.bankVersion`: 1 → 3（`campaign.test.ts` 会校验两者相等）
- 题数 10 → 12，分享码长度随之 10 → 12

### 抽题种子进分享码

题目从池子里抽出来之后，光有答案序列已经不够 —— 必须知道对方做的是哪 12 道题。
所以 v3 的分享链接多了一个参数：

```
?v=3&s=<抽题种子 base36>&a=<答案码>
```

`readSharePayloadFromUrl` 只收一个 `search` 字符串，内部用 `s` 调 `drawBank(seed)`
重建题库，再解 `a`。缺 `s`、`s` 越界、`v` 不等于当前版本，一律返回 `null`。

判定本身仍是零随机的：种子只决定「抽哪些题」，同一条链接永远重建出同一组题、
算出同一个结果。

v1/v2 均未正式对外发布，因此**不保留任何旧版兼容解码**。
调用方需要给出「这个结果来自旧版本的帽子」提示，不能静默回到封面。
