# 题库、评分与行为画像规范

> 当前版本：v3
>
> 审计日期：2026 年 9 月 4 日
>
> 运行时权威源：`src/data/questions.ts`、`src/data/constants.ts`、`src/lib/scoring.ts`、`src/lib/traits.ts`。

## 1. 题库概况

- 每场 12 道题。
- 题池有 12 个槽位，每槽 2 道候选，共 24 道题。
- 每场从每个槽位确定性抽取 1 道候选。
- 当前题库版本为 `3`，活动配置中的 `bankVersion` 必须同步为 `3`。
- 当前题库冻结日期为 `2026-08-30`，招新期内不应随意改动题目语义或权重。

题库的结构是：

```text
QuestionPool
└── 12 QuestionSlot
    └── 每槽 2 个候选 Question
        └── 每题 4 个 QuizOption
```

六类槽位：

```text
scenario · fantasy · resource · priority · abstract · decider
```

每个槽位还有一条主要观察轴；候选题必须保持相同槽位类型和观察轴，避免用户抽到不同候选后测量对象发生变化。

## 2. 选项结构

```ts
{
  id: 'a',
  text: '具体行为选择',
  whisper: '「帽子的即时反应」',
  detail: '对这个选择的进一步描述',
  p: 'dev',
  s: 'sec',
  traits: {
    create: 2,
    explore: 1,
  },
}
```

字段规则：

| 字段 | 要求 |
| --- | --- |
| `id` | 只能是 `a / b / c / d`，同题唯一 |
| `text` | 描述具体行为，不问能力，不出现部门名称或明显部门暗示 |
| `whisper` | 第二人称、帽子即时反应，不评价高下 |
| `detail` | 描述选择本身，不暗示部门，不评价正确与否 |
| `p` | 主推部门，计入 `+3` |
| `s` | 副推部门，计入 `+1`，且必须不等于 `p` |
| `traits` | 特质权重之和必须为 `3` |

## 3. 四部门评分

四个部门固定为：

| ID | 部门 |
| --- | --- |
| `dev` | 开发部 |
| `sec` | 网安部 |
| `ops` | 运维部 |
| `pr` | 组宣部 |

每题必须满足：

1. 4 个选项的 `p` 恰好覆盖四个部门各一次；
2. 4 个选项的 `s` 恰好覆盖四个部门各一次；
3. 每个选项的 `s !== p`；
4. `s` 相对于 `p` 构成无固定点置换。

一次答题中，用户选择的选项会产生：

```text
主推部门 +3
副推部门 +1
```

当前每个部门的理论满分：

```text
12 道题 × 3 = 36 分
```

结果页中的百分比使用“部门得分 ÷ 36”，不能除以四部门总分。除以总分会把四个方向互相挤压，失去方向强弱信息。

### 并列决胜

`resolveWinner()` 按以下顺序处理并列：

1. 总分高者；
2. 并列部门中主推次数更多者；
3. 决胜题所选的主推部门；
4. 固定部门顺序 `dev > sec > ops > pr`。

整个过程零随机。同一题目序列和同一答案永远得到同一结果。

## 4. 五特质行为画像

画像与部门推荐是两条独立链路：

```text
p / s       → 四部门评分 → 部门推荐
traits      → 五特质分数 → 行为画像
```

五个特质：

| ID | 名称 | 描述 |
| --- | --- | --- |
| `explore` | 探索 | 面对未知时倾向于主动接近、先走一步 |
| `insight` | 洞察 | 倾向于观察细节、追问事情背后的原因 |
| `create` | 创造 | 倾向于把想法变成具体存在的东西 |
| `guard` | 守护 | 重视稳定、持续，让事情可靠运转 |
| `connect` | 连接 | 倾向于通过人与人、信息与资源推动事情 |

每个选项的特质权重总和固定为 3，允许的形态为：

```text
3
2 + 1
1 + 1 + 1
```

特质分母按当前题目序列的理论上限计算，而不是写死一个全局常数。画像只描述“更倾向怎样做”，不表达能力高低。

行为身份由实际答案和解释证据固定推导，不能随机生成，也不能替代部门结果。

## 5. 确定性抽题与选项洗牌

抽题种子 `drawSeed` 决定每个槽位抽到哪一道候选题，并写入分享链接的 `s` 参数。显示顺序种子 `sessionSeed` 只负责当前会话中选项的展示顺序，不写入分享码。

两者必须保持独立：

- 抽题改变用户看到的题目集合，必须可由分享链接恢复；
- 选项洗牌只改变显示位置，不能改变规范选项 ID、权重和结果。

## 6. 题目文案规范

### 6.1 选项正文

- 写具体动作，不写“你是否擅长……”；
- 四个选项都应合理，不能设置明显正确答案；
- 不出现部门名称、拉丁名或部门关键词；
- 避免真实姓名、学号、手机号、QQ、微信、邮箱、宿舍、内网和后台路径；
- 适配 320px 宽度，优先控制为移动端易读的短句。

### 6.2 低语与点评

- 低语使用 `「」`，描述刚才的选择；
- 点评描述行为方式，不夸奖、不否定、不暗示部门；
- 点评不能暴露 `p / s` 映射；
- 题库校验会检查部门禁用词和字段完整性。

## 7. 什么时候必须升级版本

### 纯文案修改：可以不升级

只修改 `title`、`scene`、`text`、`whisper` 或 `detail`，并且以下内容完全不变：

- 槽位和槽位顺序；
- 候选题数量；
- 选项 ID 和语义归属；
- `p`、`s`、`traits`；
- 决胜槽。

### 语义或结构修改：必须升级

以下任一变化都必须：

1. `QUESTION_POOL.version` 加 1；
2. `CAMPAIGN.bankVersion` 同步；
3. 更新 `releaseDate`；
4. 记录旧分享链接处理策略；
5. 执行完整测试和分布模拟。

需要升级的情况包括：

- 增删槽位或改变槽位顺序；
- 增删某槽的候选题；
- 改变选项 ID 对应的语义；
- 改动 `p`、`s` 或 `traits`；
- 更换决胜槽；
- 改变分享协议。

特别注意：即使槽位数量不变，增加候选题也会改变种子抽取结果，因此同样必须升版本。

## 8. 提交前命令

```bash
npm test
npm run check:content
npm run simulate
npm run build
node shoot.mjs
node check-depts.mjs
```

改题时额外检查：

- 分布模拟中四部门都可胜出；
- 胜率没有出现明显异常；
- 旧链接没有被新题库静默误读；
- 题面、选项、低语和点评没有隐私信息；
- 移动端 320px 下没有横向溢出。
