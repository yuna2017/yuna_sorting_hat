# 题目填写规范

改题、换题、加题时按本文件填写。规则的**权威定义**在 [题目](./题目.md)，**真相在代码** `src/data/questions.ts`；本文件只规定「怎么填、填完怎么验」。

---

## 1. 要改哪些文件

| 顺序 | 文件 | 改什么 | 可否跳过 |
| --- | --- | --- | --- |
| 1 | [docs/题目.md](题目.md) | 题面、选项、权重、低语、点评（人读的镜像） | 不可 |
| 2 | [src/data/questions.ts](../src/data/questions.ts) | 同上，代码里的真相 | 不可 |
| 3 | [src/data/campaign.ts](../src/data/campaign.ts) | `bankVersion`、`releaseDate` | 仅「改动语义」时必改，见 §6 |
| 4 | [src/lib/validateBank.test.ts](../src/lib/validateBank.test.ts) | 题数、决胜题 id 断言 | 仅改题数/换决胜题时 |

不要只改 Markdown。页面读的是 `questions.ts`，文档改了但代码没改 = 没改。

## 2. 一道题的字段规范

```ts
{
  id: 'q3',                 // 'q' + 题序，全库唯一，与数组顺序一致
  title: '第一次例会',       // 4～10 字，短标题，不带标点
  scene: '……',              // 一句话场景，30～60 字，第二人称「你」
  decider: true,            // 只有决胜题写，其余不写这个字段
  options: [ /* 恰好 4 个，顺序固定 a→b→c→d */ ],
}
```

一个选项：

```ts
{
  id: 'a',                  // 必须是 a/b/c/d 之一，按数组顺序递增
  text: '……',               // 选项正文，一行内，12～28 字
  whisper: '「……」',         // 帽子低语，含直角引号，15～30 字
  detail: '……',             // 帽子点评，35～60 字（移动端 320px 约 2～3 行）
  p: 'dev',                 // 主推部门，+3
  s: 'sec',                 // 副推部门，+1
}
```

字段含义与红线见 `questions.ts` 里 `QuizOption` 的注释，不要绕过它自行发明字段。

部门 id 只有四个，不得新增：`dev`（开发部）、`sec`（网络安全部）、`ops`（运维部）、`pr`（组宣部）。

## 3. 硬约束（违反必然被测试拦下）

`src/lib/validateBank.ts` 逐题检查，破一条结果页就会失衡：

1. **每题恰好 4 个选项**，选项 id 不重复。
2. **4 个 `p` 覆盖四个部门各一次** —— 每题对每个部门都有一条 +3 路径。
3. **4 个 `s` 也覆盖四个部门各一次**，且任一选项 `p !== s` —— 即构成无固定点置换。
4. **题目 id 全库唯一**。
5. **决胜题最多一道**（当前为 `q12`）。

由 1～3 自动得到：每个部门理论满分 = 题数 × 3。**不要手写 30 这个数**，代码里用 `maxScorePerDept(bank)` 取。

### 副推怎么填才不出错

直接抄三种置换模式，循环使用即可，不要临场编：

| 模式 | dev 的 s | sec 的 s | ops 的 s | pr 的 s |
| --- | --- | --- | --- | --- |
| P1 | sec | ops | pr | dev |
| P2 | ops | pr | dev | sec |
| P3 | pr | dev | sec | ops |

填完在《题目》该题表格末尾标注 `*模式 Px*`，方便复核。

> 注意：表格按「主推部门」查行，与选项字母无关。某题里主推 `ops` 的选项若排在 B 位，按 P1 它的 `s` 就是 `pr`。

## 4. 文案写作规范

### 4.1 选项正文 `text`

- 一行内讲完一个具体动作，不写抽象品质（写「先去问宿管」，不写「善于沟通」）。
- 四个选项**难度与吸引力对等**。不要有一条明显是「正确答案」。
- 不出现部门名、部门关键词、部门配色暗示。

### 4.2 帽子低语 `whisper`

- 用直角引号 `「」` 包裹，第二人称，帽子的即时反应。
- 陈述这个选择本身，不夸奖、不否定。

### 4.3 帽子点评 `detail`

两条红线（`validateBank.test.ts` 会验第二条）：

1. **不评价高下。** 读者应该觉得「我只是选了自己更喜欢的」，而不是「这条明显更强」。
2. **不能暗示部门。** 点评中禁止出现下列词，出现即测试失败：

   | 部门 | 禁用词 |
   | --- | --- |
   | dev | 开发部、development、冒险、领导力、现场应变 |
   | sec | 网络安全部、cyber security、研究、创新、逻辑 |
   | ops | 运维部、operations、协作、细致、服务精神 |
   | pr | 组宣部、public relations、资源整合、影响力、策略 |

   禁用词表由 `src/data/departments.ts` 的 `name` / `latinName` / `keywords` 自动生成 —— 改了部门关键词，禁用词也随之变化。

`detail` 类型上可选，但**留空会被测试判失败**（要求 40 处全满）。开发期控制台也会点名。

### 4.4 隐私红线

题面、选项、低语、点评一律不得出现真实姓名、学号、手机号、QQ/微信号、邮箱、宿舍门牌、内网地址、后台路径或任何可定位到具体个人的细节。本仓库是公开部署内容，一旦提交即进入 Git 历史，删除当前文件不等于清除。写场景请用「室友」「学长」「某个学院」这类去标识化表述。

## 5. 填写模板

《题目》里加一道题，照抄这个结构：

```markdown
## Q11 · 短标题

> 场景一句话。

| # | 选项 | 权重 | 帽子低语 | 帽子点评 |
| --- | --- | --- | --- | --- |
| A | 选项正文 | `dev +3` `sec +1` | 「低语。」 | 点评两到三行。 |
| B | 选项正文 | `ops +3` `pr +1` | 「低语。」 | 点评两到三行。 |
| C | 选项正文 | `sec +3` `ops +1` | 「低语。」 | 点评两到三行。 |
| D | 选项正文 | `pr +3` `dev +1` | 「低语。」 | 点评两到三行。 |

*模式 P1*
```

`questions.ts` 里对应写法见 §2，字段顺序保持 `id → text → whisper → detail → p → s`，与现有题一致。

## 6. 改动分级：什么时候必须升版本

分享链接把答案压成 `a/b/c/d` 串，靠 `?v=` 认题库。改动分两类：

**A. 纯文案修订（不升版本）**
只改 `title` / `scene` / `text` / `whisper` / `detail` 的措辞，题序、选项字母、`p`、`s` 全部不动。旧链接仍能正确复现结果。

**B. 语义改动（必须升版本）**
下列任一情况：

- 增删**槽位**，或调整槽位顺序；
- 调整某题内选项的字母归属（原 A 的内容挪到 C）；
- 改动任何 `p` 或 `s`；
- 更换决胜槽。

处理方式：

1. `QUESTION_POOL.version` +1；
2. `CAMPAIGN.bankVersion` 同步为新值，`releaseDate` 改为冻结日期；
3. 已发出的旧链接会被 `readSharePayloadFromUrl` 拒绝（返回 `null`，页面回落到正常答题流程）——这是设计如此，宁可让用户重答，也不能拿新题库误读旧答案。

**给已有槽位补候选题不算 B 类。** 槽位数不变、顺序不变、决胜槽不变，
旧链接里的 `s` 仍能抽出原来那组题吗？——不能。候选数一变，
每槽的抽取结果就会整体漂移，旧链接会解出另一组题。
所以补候选**也要升版本**，但可以攒够一批再升一次，不必一道一题地跳。

**招新期内不改题。** `releaseDate` 之后到招新结束，只允许 A 类修订。

## 7. 提交前检查清单

```powershell
npm test              # 题库不变量 + 计分 + 分享编码 + 文案红线
npm run simulate      # 分布模拟：四部门可达、均分落在 8～12
npm run check:content # 部门文案完整性
npm run build         # 类型检查 + 构建
```

逐项确认：

- [ ] 《题目》与 `questions.ts` 内容一致（含低语与点评的每一个字）
- [ ] 每题标注了置换模式，且与代码里的 `s` 对得上
- [ ] 每题 4 个 `p` 覆盖四部门，4 个 `s` 无固定点且覆盖四部门
- [ ] 所有 `detail` 已填，且不含 §4.3 禁用词
- [ ] 无真实姓名/联系方式/内网信息（§4.4）
- [ ] 按 §6 判断是否需要升 `version` 与 `bankVersion`
- [ ] `npm test` 与 `npm run simulate` 全绿
- [ ] 若改了题数或决胜题，`validateBank.test.ts` 的断言已同步

模拟报告里若某部门胜出次数明显偏低，说明该部门的选项吸引力不足 —— 这不是校验能抓的，需要人工调整选项正文的对等性。
