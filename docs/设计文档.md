# YUNA 分部帽设计说明

## 1. 项目定位

面向协会招新的短流程互动小游戏。用户通过 12 道行为选择题了解可能适合的部门，再进入部门官网、招新入口或分享结果。

核心链路：

```text
产生兴趣 → 完成测试 → 获得结果 → 理解原因 → 了解部门 → 报名 / 分享
```

测试结果是招新链路的中间节点，不是终点。

### 与《燕山大学人生模拟器》的关系

《燕山大学人生模拟器》负责完整的校园人生体验：地点探索、随机事件、属性与技能成长、隐藏身份、毕业报告和 YUNA 工坊。《YUNA 分部帽》负责更短、更明确的部门兴趣分流。

| 项目 | 核心任务 | 适合时长 | 结果 |
| --- | --- | --- | --- |
| 燕大人生模拟器 | 体验燕大四年和不同成长路线 | 3～8 分钟 | 人生报告、技能线、隐藏身份 |
| YUNA 分部帽 | 了解部门方向并进入招新链路 | 2～5 分钟 | 部门结果、判定解释、行动入口 |

分部帽可以借鉴模拟器的内容工程、数值模拟、身份叙事和分享海报，但不引入学期、金币、复杂技能树或 20 余回合事件系统。

## 2. 玩法与判定

- 每场 12 道行为倾向题，不要求技术基础。题目从 24 道的题池里抽（12 个槽位各抽 1 道）。
- 每题 4 个选项。
- 每个选项：主推一个部门 `+3`，副推一个部门 `+1`。
- 每题 4 个选项分别主推四个部门，副推构成无固定点置换。
- 当前每个部门满分为 `12 × 3 = 36`。
- 并列决胜使用固定规则，不使用随机数。
- 选项洗牌只改变显示顺序，不改变答案 ID、计分或分享结果。
- 抽题用随机种子，但种子会写进分享链接，所以同一条链接永远重现同一组题。

权威题目和权重规则见 `src/data/questions.ts`，结构与硬约束见 [特质体系](./特质体系.md)。

## 4. 技术约束与信息源

**代码优先**：部门资料、题目、权重、计分规则的权威定义在代码中，不在文档中重复维护。

- React + TypeScript + Vite + Tailwind CSS
- Vitest 负责题库、计分、解释和分享码测试
- GitHub Actions 发布 GitHub Pages
- 不使用 Google Fonts；字体使用系统字栈或自托管的 woff2
- 不为线性流程引入额外路由或复杂状态管理
- 核心判定、结果解释、分享编码和展示过场保持解耦
- 内容扩展优先增加数据和校验，不把题目或部门事实写进组件

**判定零随机**：同一份规范答案在刷新、换设备、跳过仪式、减少动态效果和分享链接恢复后必须得到同一结果。允许随机的只有展示层（如选项显示顺序），且必须使用稳定 ID，不改变答案语义或权重。

```text
cover → opening → quiz → reveal → result
```

顶层使用状态机，不为当前线性流程引入路由。分享结果通过查询参数 `?v=3&s=<抽题种子>&a=<答案码>` 恢复，适合 GitHub Pages 的纯静态部署。`s` 必须带上，否则无法知道对方做的是哪 12 道题。

结果后的可选扩展：

```text
result → department story（可选）→ department / works / join
```

`department story` 是每个部门 2～3 个微型场景组成的“加入后的第一个任务”，用于增强代入感；它不得参与原部门判定，也不得挡住官网和报名入口。

## 5. 视觉与结果表达

### 部门主题

主题色跟随部门立绘，不使用霍格沃兹学院色。学院名称只作为文案点缀。结果页通过 `[data-dept]` 和 CSS 变量换肤。

### 结果页层级

```text
先讲故事 → 解释结果 → 展示数据 → 介绍部门 → 引导行动 → 分享
```

冠军部门是视觉主角，其他部门在雷达图和分数条中弱化。雷达图展示整体形状，精确数值由分数条展示；50 分参考线只用于阅读，不参与计算。

### 结果的两层表达

当前权威结果仍是“部门”。后续可以在不改变判定的前提下，增加一层由答案证据生成的“行为身份”，例如：

```text
部门：开发部
行为身份：数字造物者
辅助倾向：系统守夜人
```

行为身份用于解释用户为什么会被这个方向吸引，不是新增心理测评，也不替代部门结果。身份文案必须从用户实际选择中生成或由固定规则映射，不能随机编造。

### 动态效果

动态效果服务于分院仪式和阅读节奏，不得影响判定、分享结果或减少动态效果用户的可用性。

## 6. 部门内容策略

正式版本应：

- 使用协会确认的部门事实
- 优先链接到社团官网的部门介绍页
- 使用协会公共招新或报名入口
- 不放个人联系方式、内网地址或凭据
- 优先说明“部门做什么”“新生会接触什么”
- 用真实项目、作品或复盘证明部门工作，而不是只写口号

数据入口：`src/data/departments.ts`。

### 内容工程

当前题库和部门资料直接维护在 TypeScript 中。规模继续增长后，应优先建立内容校验，再考虑 Markdown / YAML 与 TypeScript 的生成流程。

已实现的自动校验（`validateBank.ts` / `validateContent.ts`，接入 CI）：

- [x] 题目、选项、部门和行动入口 ID 唯一
- [x] 每题结构和权重不变量成立
- [x] 所有部门正式文案已经核对，`contentDraft` 为 `false`
- [x] 所有外链为公开 http(s) URL
- [x] 题目数、满分、决胜题与文档声明一致（单测断言）

题目、权重、题数、满分、决胜题、活动届次与分享版本的一致性已由测试和 CI 校验；当前冻结版本为 v3。

## 7. 分享与版本兼容

分享码保存三样东西：题库版本、抽题种子、每题的规范选项 ID。

```text
?v=3&s=<抽题种子 base36>&a=<12 位答案码>
```

三者缺一不可：`a` 只是 `abcd-` 的序列，脱离题目就没有意义；`s` 决定这场抽到了哪 12 道题；
`v` 决定该用哪一版题池去抽。

- `readSharePayloadFromUrl` 只接受 `v` 等于当前 `QUESTION_POOL.version` 的链接，其余返回 `null`
- v1/v2 均未正式对外发布，因此不保留旧版兼容解码；用户会回落到正常答题流程
- 版本升级规则见 [题目填写规范](./题目填写规范.md) §6 —— **给槽位补候选题也要升版本**，因为候选数一变，旧 `s` 会抽出另一组题
- 分享链接使用可复现的结果地址；海报二维码使用经确认的公共招新群渠道
- 招新群号、二维码和 logo 素材集中放在 `src/assets/share`，更换渠道时只替换素材与文案

## 8. 数值与内容体检

借鉴人生模拟器的 `npm run simulate`，分部帽应增加题库分布模拟工具。它不替代单元测试，而是检查题库整体是否偏斜。

建议输出：

- 四部门最终胜率与平均得分
- 并列率和决胜规则使用率
- 最大、最小和平均领先分差
- 全随机、单一倾向和边界答案策略的结果分布
- 选项洗牌前后与分享恢复后的判定一致率
- 各题对最终部门的影响程度

模拟结果是改题评审材料，不自动追求四部门绝对均分。真实内容合理性优先，但明显偏斜必须被发现和说明。
