# YUNA 分部帽设计说明

## 1. 项目定位

面向协会招新的短流程互动小游戏。用户通过 10 道行为选择题了解可能适合的部门，再进入部门官网、招新入口或分享结果。

核心链路：

```text
产生兴趣 → 完成测试 → 获得结果 → 理解原因 → 了解部门 → 报名 / 分享
```

测试结果是招新链路的中间节点，不是终点。

### 与《燕山大学人生模拟器》的关系

《燕山大学人生模拟器》负责完整的校园人生体验：地点探索、随机事件、属性与技能成长、隐藏身份、毕业报告和 YUNA 工坊。《YUNA 分部帽》负责更短、更明确的部门兴趣分流。

| 项目 | 核心任务 | 适合时长 | 结果 |
| --- | --- | --- | --- |
| 燕大人生模拟器 | 体验燕大四年和不同成长路线 | 3～8 分钟 | 人生报告、技能线、隐藏身份 |
| YUNA 分部帽 | 了解部门方向并进入招新链路 | 2～5 分钟 | 部门结果、判定解释、行动入口 |

分部帽可以借鉴模拟器的内容工程、数值模拟、身份叙事和分享海报，但不引入学期、金币、复杂技能树或 20 余回合事件系统。

## 2. 玩法与判定

- 10 道行为倾向题，不要求技术基础。
- 每题 4 个选项。
- 每个选项：主推一个部门 `+3`，副推一个部门 `+1`。
- 每题 4 个选项分别主推四个部门，副推构成无固定点置换。
- 当前每个部门满分为 `10 × 3 = 30`。
- 并列决胜使用固定规则，不使用随机数。
- 选项洗牌只改变显示顺序，不改变答案 ID、计分或分享结果。

权威题目和权重规则见 [题目](./题目.md)。

### 随机性的边界

人生模拟器适合使用带种子的随机来制造不同经历；分部帽的部门判定必须保持零随机。同一份规范答案在刷新、换设备、跳过仪式、减少动态效果和分享链接恢复后必须得到同一结果。

允许随机的只有展示层，例如选项显示顺序；所有随机展示必须使用稳定 ID，不得改变答案语义或权重。

## 3. 页面结构

```text
cover → opening → quiz → reveal → result
```

顶层使用状态机，不为当前线性流程引入路由。分享结果通过查询参数 `?v=1&a=` 恢复，适合 GitHub Pages 的纯静态部署。

结果后的可选扩展：

```text
result → department story（可选）→ department / works / join
```

`department story` 是每个部门 2～3 个微型场景组成的“加入后的第一个任务”，用于增强代入感；它不得参与原部门判定，也不得挡住官网和报名入口。

## 4. 技术约束

- React + TypeScript + Vite + Tailwind CSS
- Vitest 负责题库、计分、解释和分享码测试
- GitHub Actions 发布 GitHub Pages
- 不使用 Google Fonts；字体使用系统字栈或未来自托管的 woff2
- 不为线性流程引入额外路由或复杂状态管理
- 核心判定、结果解释、分享编码和展示过场保持解耦
- 内容扩展优先增加数据和校验，不把题目或部门事实写进组件

## 5. 视觉与结果表达

### 部门主题

主题色跟随部门立绘，不使用霍格沃兹学院色。学院名称只作为文案点缀。结果页通过 `[data-dept]` 和 CSS 变量换肤。

### 结果页层级

```text
先讲故事 → 解释结果 → 展示数据 → 介绍部门 → 引导行动 → 分享
```

冠军部门是视觉主角，其他部门在雷达图和分数条中弱化。雷达图展示整体形状，精确数值由分数条展示；50 分参考线只用于阅读，不参与计算。

### 结果的两层表达

当前权威结果仍是“部门”。后续可以在不改变判定的前提下，增加一层由答案证据生成的“行为身份”，例如：

```text
部门：开发部
行为身份：数字造物者
辅助倾向：系统守夜人
```

行为身份用于解释用户为什么会被这个方向吸引，不是新增心理测评，也不替代部门结果。身份文案必须从用户实际选择中生成或由固定规则映射，不能随机编造。

### 动态效果

动态效果服务于分院仪式和阅读节奏，不得影响判定、分享结果或减少动态效果用户的可用性。

## 6. 部门内容策略

正式版本应：

- 使用协会确认的部门事实
- 优先链接到社团官网的部门介绍页
- 使用协会公共招新或报名入口
- 不放个人联系方式、内网地址或凭据
- 优先说明“部门做什么”“新生会接触什么”
- 用真实项目、作品或复盘证明部门工作，而不是只写口号

数据入口：`src/data/departments.ts`。

### 内容工程

当前题库和部门资料直接维护在 TypeScript 中。规模继续增长后，应优先建立内容校验，再考虑 Markdown / YAML 与 TypeScript 的生成流程。

上线前校验至少覆盖：

- 题目、选项、部门和行动入口 ID 唯一
- 每题结构和权重不变量成立
- 所有部门正式文案已经核对，`contentDraft` 为 `false`
- 所有外链为公开 URL，且不存在过期招新入口
- 题目、权重、文档和分享版本保持一致

## 7. 分享与版本兼容

当前分享码只保存每题规范选项 ID：

```text
?a=<10位码>
```

它能够恢复相同答案和相同部门结果，但暂时没有题库版本号。题库变化会改变旧链接的解释或结果，因此招新期内必须冻结题库。

后续分享协议应增加版本字段，同时兼容现有链接，例如：

```text
?v=1&a=dbcacadcba
```

要求：

- 旧的无 `v` 链接继续按第一版题库解释
- 新版本不能静默改变旧链接结果
- 分享卡二维码优先指向可复现的结果链接或测试入口
- 招新二维码只使用经过确认的公共渠道，可作为第二行动入口

## 8. 数值与内容体检

借鉴人生模拟器的 `npm run simulate`，分部帽应增加题库分布模拟工具。它不替代单元测试，而是检查题库整体是否偏斜。

建议输出：

- 四部门最终胜率与平均得分
- 并列率和决胜规则使用率
- 最大、最小和平均领先分差
- 全随机、单一倾向和边界答案策略的结果分布
- 选项洗牌前后与分享恢复后的判定一致率
- 各题对最终部门的影响程度

模拟结果是改题评审材料，不自动追求四部门绝对均分。真实内容合理性优先，但明显偏斜必须被发现和说明。
