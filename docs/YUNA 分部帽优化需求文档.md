项目：燕山大学网络与信息协会·分部帽  
项目定位：协会招新互动网页

## 一、项目目标

目前的分部帽已经具备完整的基本测试流程：

> 封面 → 开场 → 答题 → 分部结果

下一阶段不应单纯追求“网页更漂亮”，而应将项目进一步发展为：

> **招新互动小游戏 + 部门展示入口 + 社交传播工具**

最终形成：

> 用户进入 → 产生兴趣 → 完成测试 → 获得结果 → 了解对应部门 → 查看部门项目 → 进入招新渠道 → 分享给其他人

因此，本次修改的核心不是重写项目，而是在现有架构基础上补齐“体验、传播、招新”三个环节。

# 三、核心定位调整

## 3.1 不再把项目单纯定位为“测试网页”

当前项目：

> 测试用户适合哪个部门。

调整后：

> 通过分院帽式互动测试，让新生了解自己可能适合的部门，并进一步了解协会各部门。

因此，“测试结果”不是终点，而应该是整个招新流程的中间节点。

## 3.2 核心用户流程

目标流程：

```
进入分部帽
    ↓
产生兴趣
    ↓
开始测试
    ↓
完成测试
    ↓
分院仪式
    ↓
获得部门结果
    ↓
为什么是这个部门？
    ↓
了解部门
    ↓
查看真实项目
    ↓
招新 / 联系 / 报名
    ↓
分享结果
```

# 四、结果页改造

这是本次修改中最重要的部分。

目前结果页已经具备：

- 部门名称
- 部门立绘/卡片
- slogan
- 关键词
- Hogwarts House
- 雷达图
- 分数
- 部门介绍接口
- 部门链接接口

现有代码已经为 `intro` 和 `links` 留出了位置，因此不需要改变整体架构。

## 4.1 结果展示顺序

建议调整为：

```
分院仪式
    ↓
你的部门
    ↓
为什么是这个部门？
    ↓
你的关键词
    ↓
部门契合度
    ↓
关于这个部门
    ↓
他们正在做什么？
    ↓
招新入口
    ↓
分享结果
    ↓
再测一次
```

核心原则：

> **先讲故事，再展示数据，最后引导行动。**

不要让雷达图成为结果页最重要的信息。

# 五、增加“结果揭示仪式”

这是项目最值得加强的体验之一。

## 5.1 目标

用户完成最后一道题后，不应立即看到最终结果。

应该增加短暂的“分院帽判定过程”。

例如：

```
最后一题
 ↓
进入黑暗/星空背景
 ↓
帽子出现
 ↓
等待
 ↓
“Hm...”
 ↓
出现部门候选
 ↓
短暂犹豫
 ↓
THE HAT HAS DECIDED
 ↓
部门揭晓
```

不要求完全模仿电影，只需要建立“仪式感”。

## 5.2 特殊情况

如果用户的两个部门得分非常接近，可以强化：

> “帽子似乎犹豫了……”

项目现在已经存在 `tiedWith` 机制，并且结果页已经针对这种情况设计了文案。

因此后续可以进一步视觉化，而不是重新设计判定逻辑。

# 六、完善部门信息

这是从“小游戏”向“招新工具”转变的关键。

每个部门至少应该拥有：

```
部门名称
部门副标题/拉丁名称
一句话定位
部门介绍
关键词
典型活动
代表项目
招新信息
联系方式/入口
作品链接
```

## 6.1 部门介绍

避免写成传统宣传稿。

不要重点写：

> “本部门是一个充满活力、团结协作、技术氛围浓厚的团队……”

更推荐：

> “我们主要做什么？”

> “你进来之后会接触什么？”

> “过去一年做过什么？”

> “适合什么样的人？”

让新生能够快速判断：

> **“这个部门是不是我想去的地方？”**

---

# 七、增加“真实项目展示”

建议结果页增加：

## 「他们做过什么？」

每个部门展示 2～3 个真实项目。

每个项目包含：

```
项目名称
项目截图
一句话介绍
项目链接
```

例如：

```
YUNA 社团网站

用于……
    
[查看项目]
```

这样比单纯写部门介绍更有说服力。

核心原则：

> **少宣传口号，多展示实际成果。**

---

# 八、增加招新入口

结果页最终应该有一个明确的行动入口。

例如：

> **对这个部门感兴趣？**

然后：

```
[了解更多]
[加入招新群]
[报名]
[查看往期项目]
```

具体按钮根据协会实际招新流程确定。

不能让用户看完结果后不知道下一步应该干什么。

这是项目非常重要的传播能力。

目前项目实际上已经具备分享码基础：


并且能够根据 URL 恢复结果。

因此下一步主要是补 UI。

## 9.1 结果页增加

> **分享我的分部帽结果**

至少实现：

```
[复制结果链接]
```

移动端可以进一步支持系统分享。

## 9.2 分享文案

建议自动形成类似：

> 我在 YUNA 分部帽里被分到了「开发部」。
> 
> 你会被分到哪个部门？

然后附测试链接。

目的不是让用户主动宣传协会，而是让分享结果本身具有社交属性。

# 十一、优化题目设计

现有工程对题库约束已经比较完善。

README 中规定：

> 每题 4 个选项各主推一个不同部门，同时副推构成置换。

并且已经通过测试保证题库结构。

因此不要为了优化题目而破坏现有计分系统。

## 11.1 避免明显对应关系

尽量避免：

> 喜欢写代码吗？

直接对应：

> 开发部

或者：

> 喜欢 CTF 吗？

直接对应：

> 网安部

否则用户可以直接猜答案。

## 11.2 增加情境题

推荐更多：

> “如果一个系统突然出现问题，你会……”

> “如果给你一个完全陌生的项目，你第一步会……”

> “团队准备做一个项目，你更愿意负责……”

这种题目更能测试行为倾向。

## 11.3 避免“正确答案”

题目应该让用户觉得：

> “我只是选了自己更喜欢的东西。”

而不是：

> “这个选项明显更厉害。”

# 十二、增加“隐藏属性”

可以作为后续玩法。

最终除了：

> 你属于开发部

还可以显示：

> **你的隐藏倾向**

例如：

```
探索欲：★★★★★
创造力：★★★★☆
稳定性：★★★☆☆
风险偏好：★★★★☆
```

或者：

> “你是一个喜欢自己折腾的人。”

但需要注意：

这属于娱乐性结果，不应包装成真正的心理测评。

# 十三、弱化“伪科学感”

当前项目有：

> 雷达图  
> 百分比  
> 单部门满分  
> 契合度

这些数据有趣，但容易让用户误以为这是科学测评。

建议增加一句非常轻量的说明：

> 本结果根据你的答题选择生成，仅用于娱乐与自我探索。

不要过度强调“准确率”“人格类型”等概念。

# 十五、移动端优化

本项目应该以手机作为第一目标平台。

重点测试：

- 320px
- 360px
- 390px
- 412px

以及：

- Android Chrome
- iOS Safari
- 微信内置浏览器

## 重点检查

### 操作

- 选项是否容易点击
- 按钮是否足够大
- 是否容易误触

### 阅读

- 字体是否过小
- 行距是否合理
- 是否需要大量滚动

### 视觉

- 雷达图是否正常
- 部门立绘是否正常
- 动画是否卡顿
- 长文本是否破坏布局

### 网络

尤其考虑校园网环境。

尽量：

- 减少第三方资源
- 图片压缩
- 字体自托管
- 避免阻塞首屏

目前项目已经明确避免 Google Fonts，并考虑国内网络环境，这个方向继续保持。

# 二十一、开发顺序建议

如果你准备实际动手修改，我建议不要一次把所有功能都做掉。

按照：

**阶段 1：结果页**

> 结果揭示 → 结果解释 → 部门介绍 → 招新入口

↓

**阶段 2：传播**

> 分享按钮 → 分享链接 → 分享卡

↓

**阶段 3：内容**

> 题目优化 → 项目展示 → 部门特色 → 特殊结果

↓

**阶段 4：体验**

> 动画 → 音效 → 移动端细节 → 性能优化

↓

**阶段 5：数据**

> 访问统计 → 完成率 → 分享率 → 招新转化

这样比较合理。

最重要的一点是：**不要把这次迭代变成一次技术重构。** 你们现有的题库、计分、分享码、数据结构和部署体系已经基本搭起来了。下一步应该把精力放在“用户做完这个测试之后，会发生什么”上。
